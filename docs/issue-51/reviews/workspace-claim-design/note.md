## Required ownership state machine

Use an explicit state transition equivalent to `Unclaimed → ClaimAcquired(G) → Recovering(G) → Active(G) → Closing(G) → Released`, with `Lost/Unknown` as a terminal state for that parent's mutation/dispatch authority. `G` is a cryptographically random run generation, not PID/time. Test owners remain separate authenticated capabilities bound to `(workspace identity, G, test nonce)`; possessing a new workspace claim alone must not turn unknown test evidence into stop authority.

1. **One stable coordination identity.** All aliases accessing the same actual-machine/user/repository workspace must contend on the same coordination object. A source/client path or SSH alias alone is insufficient. Retain the lock object outside the directory CLEAR removes. Never unlink/recreate a live lock file or replace its inode during cleanup: retained old and newly opened locks must not protect different objects with the same name. Path/root replacement must fail closed. Define supported filesystem/lock semantics; an unsupported backend must refuse instead of reverting to heartbeat/PID authority. These are design obligations, not claims that a particular OS API is already wrong.
2. **Claim before cleanup-enabled ownership.** Acquire the actual machine's exclusive claim before reading/recovering/deleting old state, creating the run folder, or authorizing writes/dispatch. Publish `G` while transition exclusion is held. Failed acquisition yields a non-owner whose Drop can only release resources it actually acquired; it cannot call CLEAR, stop prior test owners, rewrite the generation, remove the run folder, or retire any claimant's evidence. Initialization failure after acquisition can clean only while the exact claim remains owned. Equal PID and clock/heartbeat age never supply ownership.
3. **Every action checks G under the operation fence on the actual machine.** A parent-side check followed by a queued SSH/native request leaves a race. Check the durable generation after acquiring the fence and immediately before the operation's irreversible boundary. Include worktree add, checkout, clean, incoming bundle writes/removal and destination fetch/ref mutations, test log/record creation, ordinary close and startup `clear_leftovers`. Generation checks must not occur only at `Workspace::open` or only before enqueueing. Reads used to form destructive recovery proof must be fenced through its final verification and mutations.
4. **Turnover excludes in-flight operations.** A new claimant waits for the operation fence, invalidates old authority and publishes its new generation before permitting new work. An old-generation request admitted after replacement must record zero mutations/dispatch. A previously admitted operation either finishes while retaining its fence or has a recorded ownership outcome that prevents takeover cleanup until it is safe. The fence must be held by the component that actually waits for the mutating command; a parent dying must not release the only lock while its unfenced mutation continues elsewhere. Fail closed if that cannot be established. Never break the fence/claim merely because a timeout or heartbeat expires.
5. **Claim and fence lifetime are explicit.** The long-lived remote helper retains the claim lock. A local `File` retained by the actual owner can provide the analogous lifetime, provided clones, error paths and Drop preserve the same identity. Keep claim/fence handles out of executed user code, which otherwise could retain them indefinitely; conversely do not close them prematurely on a queued/ambiguous mutation. Define one lock ordering for claim transition, operation fence and recovery callbacks, avoiding a takeover waiting on a fence whose owner waits on that takeover. “Short fence” means bounded scope, not evidence that checkout/cleanup is quick.

## Durable dispatch: necessary handoff details

Holding the operation fence through durable owner-record creation is the correct boundary **only if creation also establishes a live recoverable dispatch owner whose stop is sticky across the remaining startup path**.

Required order: acquire fence → validate current `G` → establish authenticated supervisor/anchor and pending-dispatch state → publish complete exclusive owner record → acknowledge the handoff → release fence. User code starts only in the supervised state covered by that record. Record/gate ordering may vary, but no started or committed-to-start command can be invisible to takeover recovery.

- Record publication is complete, bounded and atomically visible. Partial writes, failed close/flush, occupied names, replaced paths or failed acknowledgement remain Unknown or guaranteed NotDispatched. If “durable” includes machine/power loss, specify file and containing-directory durability rather than relying on mere visibility; otherwise disclose the weaker crash boundary. Do not silently promote a torn record to no owner.
- A new claimant can recover a record whose helper has published it but whose command is still queued or gated. Stop before user start must permanently close that gate/cancel that queue. A terminal receipt cannot be produced for an idle helper and then followed by a late command launch. The local Service and both remote interpreters must obey this same invariant.
- An old parent that loses its lease after checkout but before test submission gets a rejected `G`, never a second dispatch. If the request had already crossed the handoff, recovery finds its exact owner and waits for authenticated terminal proof. Lost acknowledgement does not justify replay, treating the record as absent, or deleting it.
- Releasing the fence after sending a request, allocating a path, seeing a marker, or putting a task on a channel is insufficient unless that exact event proves the above handoff. A machine-side helper must validate generation/fence on the actual creation/start path; serializing only Rust callers does not fence remote delayed messages.
- Stop/reap proof is separate from generation validation and cleanup proof. Missing/wrong receipt, unavailable owner, failed target start with uncertain descendants, supervisor/lease loss or changed record conservatively preserve recovery evidence. A process exit/EOF is not by itself the test-owner receipt. A recovered old owner cannot receive new work after its terminal receipt.

## Recovery and checked CLEAR

The claimant must recover **every started or committed old owner** before checkout/removal/ref cleanup. It must fence the whole inventory/proof/mutation window so no late old-generation record can appear after inventory. Validate every name/record before issuing control. Unknown/legacy/replaced evidence leaves recovery blocked and visible; do not age it away. Startup leftovers follow precisely the same claim and fence rules as normal open/close.

Checked CLEAR must explicitly propagate each listing, worktree removal, filesystem mutation, metadata deletion and ref update failure. Pipeline producer failures must not be hidden by a successful consumer; loop/subshell failures must reach the top-level result. Check required postconditions and produce a structured outcome bound to `(workspace identity, G, exact recovered record set)` rather than final shell status alone. A retained File lock on the app machine does not make remote shell mutations generation-safe.

**Keep a recovery ledger outside any deletion sequence that can fail partway.** Current CLEAR removes `$b` (and its owner records) before later metadata/ref cleanup. Merely checking those later commands would report failure after already erasing the only indexed owner capabilities. Preserve exact authenticated record bytes and progress durably until all required mutations have succeeded. Delete/retire that evidence only after confirmed whole-cleanup postconditions. This can be a staged ledger/manifest or an ordering that demonstrably preserves equivalent recovery; no particular format is mandated. Partial cleanup must report exactly that, not promise the workspace is wholly preserved or that the next run will automatically fix it.

Namespace mutations need generation-aware ownership too. Current broad `refs/gitcraft-bisect/` deletion except same-PID send refs (`workspace.rs:396–398`) must not become authority to remove another generation's in-flight refs. Bundle/source send refs may reside outside the destination workspace (`workspace.rs:504–522`); enumerate those routes explicitly and either fence them with the appropriate owner or partition them by unambiguous generation. Do not use a random generation merely as a log label while cleanup still sweeps a shared namespace.

On CLEAR uncertainty: no cleaned receipt, no owner-artifact retirement, no success-only UI completion, and no claim that an original process exited safely from a cleanup command's zero exit. Preserve the primary and cleanup errors. A cleanup retry must acquire fresh valid authority and verify prior evidence, not revive a stale parent object. Drop should be idempotent and conservative; failure must remain observable outside Drop where a user-visible result exists.

## Required recording invariants before source re-review

These are **future pure/injected schedule requirements**, not tests executed by this reviewer. Assert negative side effects and state/evidence, not just callback order. Wire recordings into the real production decision branches for local and both remote backends.

| Schedule or fault | Required recorded result |
| --- | --- |
| Two app processes acquire the same empty workspace; loser fails claim or mkdir; loser Drop runs after winner starts | Only one generation published; loser records zero stop/CLEAR/create/dispatch/retire; winner claim/test untouched. |
| Equal client PIDs; stale/frozen/jumping clocks; heartbeat absent or delayed while lock is held | No claim takeover; PID/time have zero authority. |
| Old parent validates, then request queues; new generation replaces it; old request finally reaches machine helper | Machine-side stale-G rejection; zero record creation, checkout, log write or target start. |
| Checkout/clean/CLEAR is admitted and pauses; takeover is requested; parent/transport disconnects | No new mutation/turnover until the admitted operation's fenced terminal state; if ownership is uncertain, preserve evidence and deny unsafe cleanup. |
| Lease dies before owner creation, midway through record publication, after publication/before acknowledgement, after acknowledgement/before user start, and immediately after start | Each outcome is guaranteed NotDispatched or discoverably supervised; no unrecorded start, replay, or terminal receipt followed by late start. |
| Recover/stop arrives while old target is pending in native Service queue or remote launch gate | Cancellation is sticky; no later start after stop proof. Same endpoint/record identity binds all outcomes. |
| New claimant inventories records while old dispatcher is paused at every publication boundary | Fence excludes new records during proof and destructive phase; takeover recovery includes every admitted owner. |
| Record name collision, truncated write, failed flush/close, invalid/missing/replaced record, wrong endpoint/receipt, legacy PID file | Zero destructive cleanup and no fabricated stop/cleanup success; unknown remains visible and ledger retained. |
| Claim-lock pathname or generation file replaced; stale Drop or release executes after replacement | No split lock authority; stale generation cannot release/overwrite/delete current claim; unsupported identity condition fails closed. |
| Each CLEAR command/listing/pipeline fails independently, including failure after base directory removal but before ref completion | Aggregate non-success, precise partial state, durable ledger retained, zero artifact retirement and no cleaned receipt. |
| Worktree removal succeeds but ref deletion fails; retry and repeated close/Drop follow | Retry uses exact remaining ledger/authority; no unrelated deletion; no erasure of failure by idempotent success. |
| Retire fails after cleanup proof; shutdown/EOF occurs in each claim/fence phase | Artifact retention/error is honest; no owner kill, broad cleanup or stale-G dispatch is authorized by retirement/shutdown. |

Use synthetic lock identities, generations, file-operation results, queues, endpoints and receipts; no real children, signals or filesystem race fixtures are needed to establish these schedules. Bound waits and inventory/proof memory; a bound failure must preserve the same Unknown state. Do not clear Unknown just to unblock a new run.
