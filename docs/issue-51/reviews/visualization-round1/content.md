## Blocking findings

### 1. [P2] Atlas hotspots can open an empty history because all-ref analysis navigates only through HEAD

`src/repo/atlas/mod.rs:157` captures `(path, data.head)` for every file, and line 161 opens history at that HEAD. However `src/git/atlas.rs:33` uses activity over local/remote branches, tags and HEAD, and lines 101–107 add paths from every scanned commit. A file exclusively on a different branch therefore appears as a changed hotspot, but clicking it says “No commits touch this file yet.” Its actual changes never appear. This directly misses #46's “hotspot opens file history” requirement on ordinary multibranch repositories.

Concrete reproduction: create main with `base`; branch side, commit `side-only`; checkout main; open atlas and choose Change frequency; click side-only. Exact local Git fixture `/tmp/gitcraft-review-atlas-branch-fixture.json` records immutable tips and fixture path. `git log --all --format= --name-only` includes side-only, `git log --follow --format=%s <HEAD> -- side-only` is empty, and the same command at the recorded side tip yields `side adds file`. Preserve a relevant immutable revision per historical file, or open a bounded all-analyzed-roots history with the intended coverage; do not bind every historical path to HEAD.

### 2. [P2] Atlas file/directory reuse hides current files behind historical folders

`src/git/atlas.rs:146` returns an existing node solely by path, with no file/directory distinction. A current HEAD file `a` and historical `a/old` produce the same node `a`, with current bytes and a historical child. `src/repo/atlas/mod.rs:154` and line 157 decide whether something is a file solely from `children.is_empty()`. Clicking current file a therefore always zooms into a historical folder; there is no action to open a's history. The displayed current file also inherits historical subtree churn/contributor attribution as though it were a folder.

Reproduced with the exact atlas build/ensure implementation in a temporary standalone harness, with only the activity transport/model stubbed: current tree `a` =100 bytes, scanned historical path `a/old`. Result: root children=[1]; node1 path=a bytes=100 children=[2] changes=1; node2 path=a/old bytes=0. This is also a normal real repository sequence: commit directory a/old, remove directory, commit file a. Retain explicit file identity/type and make both current-file and historical-subtree histories reachable. The existing atlas UI test covers only an uncomplicated src/a tree.

### 4. [P2] Atlas metadata expansion bypasses the advertised memory limits

`src/git/atlas.rs:105–107` clones the complete contributor identity once per touched path, and lines 112–115 format and retain it again in every node. The 16/64 MiB Git-output limits, 100,000-file cap and 200,000-node cap do not cap the product of identity length and touched paths. A single legal commit with a long author name and many tiny file paths can therefore allocate gigabytes from a small history stream and kill the application despite analysis running in the background.

Safe exact-build experiment (no OOM attempt): one record with 16,384-character name and 512 short paths, only 18,944 identity+path input bytes, yields 513 nodes retaining **16,809,984 bytes in contributor String capacities alone**. Temporary harness `/tmp/gitcraft-review-atlas-source.rs` contains the unchanged atlas source followed by this review-only entry point; `/tmp/gitcraft-review-atlas.rs` provides small activity stubs. A 1 MiB identity ×4,096 paths, still comfortably below a single 16 MiB command output cap, extrapolates to multiple GiB. Intern identities and retain compact IDs/counts in nodes, cap rendered label length, and enforce an aggregate retained-analysis byte budget with a clear partial/error state. Do not execute the extrapolated OOM case as a test.
