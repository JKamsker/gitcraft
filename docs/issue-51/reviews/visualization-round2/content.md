## New blocking finding

### P2 — postcard commit limit does not bound parent-edge work; layout cannot be cancelled

Source: `src/git/postcards.rs:26–29,46–66`; `src/repo/postcards/render.rs:23–29`; `src/graph.rs:84–101,129–135`.

The range reader accepts up to 200 listed commits but allows an arbitrary number of parent IDs per listed commit, limited only by the 16 MiB Git-output cap. The renderer calls `graph::layout()` before another cancellation check. Layout scans the complete current lane array to look for each new parent, then scans it again to find a free lane. A single row with P distinct parents performs P(P−1) lane visits. It opens lanes for excluded parents too. There is no aggregate parent-edge/lane/work budget or active callback inside this work.

This is reachable through a valid, very narrow release range, not just a fabricated parser input. A bounded real Git fixture created a chain of 128 commits, then used `git commit-tree` to create a merge whose parents are all 128 distinct chain commits. Its first parent is the chain tip selected as the excluded base. `git log base..target --format=%H%x00%P%x00%aN%x00%ad%x00%s%x00` returns **one** commit with **128** parents; the parent field is only 5,247 bytes. All commits and parents exist. Details and immutable IDs: `/tmp/gitcraft-visual-content-r2-parent-fixture.json`; actual log output: `/tmp/gitcraft-visual-content-r2-parent-fixture.log`.

Independent exact-source layout harness `/tmp/gitcraft-visual-content-r2-parent-budget.rs` used only small, bounded inputs:

| Listed commits | Parents/lanes | Parent text bytes | Deterministic lane visits | Observed layout time here |
| --- | ---: | ---: | ---: | ---: |
| 1 | 64 | 2,624 | 4,032 | <1 ms |
| 1 | 512 | 20,992 | 261,632 | 1 ms |
| 1 | 4,096 | 167,936 | 16,773,120 | 81 ms |

Log: `/tmp/gitcraft-visual-content-r2-parent-budget.log`. The lane-visit count is derived from the source's two unsuccessful linear searches for each distinct parent, not a profiler measurement. Extrapolation only: roughly 400,000 SHA-1 parents remain below the 16 MiB source cap and imply roughly 160 billion lane visits before cancellation can be observed. **That large case was not constructed or executed.** The result runs off the UI thread, but can monopolize its owned analysis worker after close/cancel; image height and the 200-row limit do not bound it.

Required correction: validate cumulative parent-edge/lane/layout work before composition and refuse unsupported ranges explicitly, and/or provide indexed bounded layout with cancellation inside its work. Do not silently discard supported graph nodes/edges to satisfy the budget. Cover a one-row range whose excluded ancestor parents exceed the work budget with a small injected-budget test; test cancellation before and during layout without a giant repository/OOM fixture. A parent-count ceiling alone also needs to account for repeated edges and cumulative rows.
