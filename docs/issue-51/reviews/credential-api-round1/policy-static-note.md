# Static credential-consumer policy feasibility note

**Design disposition:** the original root-Git PPID rule is refuted. The revised HTTP-transport wrapper is plausible on Unix for a narrower trusted-consumer policy, but is not accepted implementation and does not establish “top-level operation only” authorization. Original API-R1 findings remain open. No Git/process/network fixture, compilation, signal, cancellation test, CI, source edit or subagent was run for this note; only static primary-source retrieval and writing this note occurred.

## Original proposal: root owner PID

Official `transport-helper.c:get_helper` starts `git remote-https` as a child. The external-command dispatcher may add another process before the actual transport. `remote-curl` owns HTTP and calls the credential machinery; `credential.c:run_credential_helper` starts the credential shell from that process. Thus ordinary HTTPS is approximately:

```
root git fetch/push/clone
  → git remote-https dispatcher
    → git-remote-https / remote-curl
      → credential helper shell
```

The helper's immediate parent is the HTTP transport, not the root Git process. `PPID == rootGitPID` would reject legitimate authentication. A direct `git credential fill` fixture has a different shape and cannot validate that design. Sources: [transport-helper.c, get_helper](https://raw.githubusercontent.com/git/git/master/transport-helper.c), [git.c, execv_dashed_external](https://raw.githubusercontent.com/git/git/master/git.c), [remote-curl.c, cmd_main/http_init](https://raw.githubusercontent.com/git/git/master/remote-curl.c), [credential.c, run_credential_helper](https://raw.githubusercontent.com/git/git/master/credential.c).

## Revised proposal: private remote-http/https wrappers

On Unix, a shell wrapper can set owner=$$ and exec the pinned native HTTP helper. Successful exec preserves its process identity, and Git launches the `!function` credential helper through a child shell. Comparing that shell's immediate PPID with the captured transport owner is therefore structurally compatible with ordinary remote-curl authentication. Keep the ownership check in the directly launched helper shell; moving it into another shell/program adds another parent and changes the predicate. [Git shell preparation and Unix child launching](https://raw.githubusercontent.com/git/git/master/run-command.c).

`GIT_EXEC_PATH` is a supported discovery control. Git prepends it to PATH and propagates it to external programs; adding the original exec-path to the remaining PATH can retain other installed helpers. This must use the selected Git installation's original absolute HTTP executables, captured before overriding discovery, and safely quoted original argv. Looking up `git-remote-https` again through the modified PATH would recurse or select an unintended binary. [exec-cmd.c, git_exec_path/setup_path](https://raw.githubusercontent.com/git/git/master/exec-cmd.c).

### Exact limits that must be decided before coding claims

1. **Every nested Git inherits the wrappers.** An unconditional wrapper setting owner=$$ also authorizes a nested `git fetch`/submodule transport. It does not matter that the nested process began without owner: entering the wrapper mints a fresh owner. Exact endpoint/account checks can still refuse different endpoints, but the same authorized URL in a nested transport is accepted. Consequently this is “only designated HTTP-transport consumers may retrieve the credential,” not “only the top-level command may use it.” If blanket secondary/submodule refusal remains required, the design needs an explicit authorization source for allowed transport launches; merely checking an inherited marker or descendant relationship is insufficient. A simple parent==root check also misses dispatcher processes and operations such as `git pull` spawning `git fetch`. No supported credential-protocol field identifies this origin.
2. **Ordinary LFS lookup is distinguishable in the proposed narrower policy.** LFS asks `git credential fill`, whose helper parent is that credential Git process, rather than the HTTP transport owner. With owner removed at outer entry and absent/mismatched owner refusing with `quit=true`, that request fails. This addresses the LFS lookup route described in API-R1-1 without silently skipping LFS objects/hooks. It is not a sandbox against a trusted hook that reads the inherited secret or deliberately invokes the transport wrapper; that stronger threat model is expressly excluded. Git documents that `quit=true` prevents later helpers and prompts. [Credential helper contract](https://raw.githubusercontent.com/git/git/master/Documentation/gitcredentials.adoc).
3. **Owner/environment cleanup is mandatory on every entry.** Remove a caller-inherited owner before starting the outer Git command. Missing owner must fail closed; do not retain a helper-only compatibility fallback. Transport children inherit owner, but their own helper grandchildren must not pass merely because the variable exists. Any shared API caller installing the helper without the new transport contract will now refuse intended authentication and needs migration or an explicit unsupported result.
4. **Windows is not covered by the Unix proof.** Native Git uses `mingw_spawnvpe`; its native exec compatibility implementation creates/waits for another process rather than Unix replacement. MSYS shell $$ / PPID and native Windows PID relations require their own supported identity mechanism and platform evidence. Do not assume numerical equivalence or publish Windows acceptance; fail explicitly where this policy cannot be established. [Git for Windows compatibility implementation](https://raw.githubusercontent.com/git-for-windows/git/main/compat/mingw.c).
5. **Retain independent endpoint/account and config controls.** The owner check adds consumer identity; it does not replace correct Git path normalization, account checks, helper-chain reset or refusal of mismatched URLs. Reset applicable configured helpers and handle configured/URL usernames deliberately. Redirect refusal must win effective matching URL-specific HTTP settings in the actual transport. Preserve the selected profile and Git installation while introducing wrappers. These are separate gates, not consequences of PPID equality.
6. **Temporary wrapper artifacts need an owned lifetime.** Use exclusive private directory creation and restrictive modes, create-only files, pinned absolute original executables and complete quoting. Keep the directory leased until all authorized users finish, preserve argv/exit/stdout/stderr, and bind cleanup to owned artifacts rather than broad PATH/glob or unchecked replacement paths. A shell trap after only the outer command is not by itself proof that no owned child can still need a wrapper. Remote SSH/WSL needs artifacts and absolute targets on that repository machine; a local path cannot silently substitute.

## Minimal feasibility conclusion and future gates

Supported helper input provides URL/account context, not an authenticated consumer identity. Thus a robust per-consumer boundary needs a launch boundary such as the proposed transport wrapper (or a larger owned transport/broker integration), not a helper-only root-PID comparison. The revised wrapper can be pursued as the explicitly narrower Unix trusted-HTTP-consumer policy if its nested-transport behavior is accepted and clearly stated. It is not yet a complete secondary-consumer authorization design across all platforms.

Before runtime, require static and recording gates for: exact generated argv/environment/config; ordinary remote-curl versus LFS `git credential fill` and nested HTTPS shapes; owner absence/mismatch; unrelated URL/account refusal; helper precedence; redirect overrides; selected binary/remote-machine paths; wrapper lifetime, failure and cleanup; and Windows explicit refusal or a platform-specific proof. Recording inputs must model the real transport chain, not only direct credential fill. Any later owned runtime fixture needs separate parent authorization and established process containment. This note does not clear the current hold or accept unpublished source.
