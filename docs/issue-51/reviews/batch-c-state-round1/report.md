## New batch findings

### C1 — P1: changelist index exchange can publish foreign lock bytes, then delete original index backup

`src/git/drafts/lists/index.rs:54–59` creates index.lock and holds a File for writes, but obtains its identity through the mutable pathname. `:75–83` verifies only the original index, exchanges mutable index.lock/index paths (`:85–88`) and verifies the displaced original now at index.lock. It never verifies that the new public index is the written candidate/retained inode before returning success. `lists/mod.rs:563–580` can then publish HEAD/state and call accept, which removes the old index backup.

**Source interleaving, not executed:** after candidate creation/writing, another writer moves that candidate lock aside and installs a foreign regular file B at index.lock. EXCHANGE puts B at index and original A at index.lock. The postcheck sees unchanged A and passes; ref publication does not read the index. accept deletes A; a committed-list success can leave B as the index. A symlink substituted at the lock name can likewise be exchanged into the public index because swap does not require the entry itself to be a regular owned candidate. A late parent-directory replacement also redirects full-path operations because no directory handle is retained.

The same implementation has observation→remove races at accept `:92–93` and Drop `:111–112`: a foreign replacement after matches is unlinked. Rollback `:107` observes the current index, then exchanges mutable names without capturing/inspecting what actually moved; a late unrelated index can be displaced while the error path silently returns. This is a distinct new publisher, not the corrected fileviews publisher.

**Fix:** reuse a coherent held-directory, no-follow, retained-handle publication primitive. Prepare in a private sibling, capture/inspect displaced entries, install create-only, verify actual installed identity/bytes/policy and preserve every foreign/uncertain entry. Cleanup must capture/inspect before removing private owned entries; no check-then-unlink of public names. Preserve typed uncertainty through the caller. First add deterministic recording/synthetic interleavings at each boundary; real index fixtures remain held.

### C2 — P1: replacement indexes and working files preserve mode only, losing full access policy

New `lists/index.rs:70–72` copies std permissions only onto a newly created inode. Source snapshots (`drafts/mod.rs:80–88,338–407`) do not capture index uid/gid, ACLs or xattrs for comparison. Working materialization (`working_transaction.rs:175–195`) likewise constructs a new inode with only mode. Shelves/virtual permission maps store u32 bits (`lists/mod.rs:21–26,657–673`; `virtuals.rs:27,44`; `permissions.rs` masks0o777). Successful working cleanup deletes the displaced original inode (`working_transaction.rs:269–278`).

A regular file or index with an ACL denying a principal permitted by mode can lose that restriction after list commit/shelve or virtual activation. File ownership/group may change to the process/default directory values; xattrs and native policy are not copied or guarded. A metadata-only concurrent tightening is not included in the preview equality checks. Saved content blobs and permission bits cannot reconstruct the omitted policy after the original is removed. This is source proof of omitted preservation, not a native ACL test.

**Fix:** capture complete supported identity/access policy through retained no-follow handles, create a compatible candidate, verify full metadata before/after publication, and preserve it through shelf/virtual undo. Refuse unsupported/conflicting policy before user-state mutation. Keep native platform gates pending; a mode-only test is insufficient. The working-file primitive is shared with the rejected history/turn implementation; this finding records new list/virtual reachability and the new index publisher.

### C3 — P1: virtual branch transaction can follow a late symbolic ref into an unrelated checked-out branch

`virtuals.rs:504–524` checks worktree occupancy and rejects symbolic destinations before publication. The eventual transaction (`:527–554`) uses ordinary dereferencing update commands, with no transaction-bound direct-ref expectation. The prepared hook (`:555–560`) compares HEAD branch and worktree inventory; it does not bind the destination's symbolic/direct identity.

**Source interleaving:** virtual alpha has old OID A. After the symbolic-ref check, alpha becomes a symbolic ref to unrelated victim whose tip is also A. Victim is neither the anchor nor another virtual ref participating in this transaction. The expected-old comparison succeeds on victim, update writes the candidate there, and the state describes alpha as updated. If victim is checked out, the worktree precheck examined branch alpha rather than victim; an unchanged inventory does not detect redirection. The same issue affects undo. Native HEAD/referent locking does not protect this separate target.

Changelist/virtual state refs also rely on a precheck (`lists/mod.rs:66–76`, `virtuals.rs:68–75`) followed by dereferencing updates (`lists:239–243`, `virtuals:528–541`); late indirection can redirect matching application-state objects. Deferred save already explicitly uses option no-deref, showing the intended distinction.

**Fix:** bind direct destination/state refs and expected OIDs in the native transaction itself, preserving the special symbolic HEAD/referent guard separately. Use recording cases for late target indirection, including an unrelated checked-out victim with the same OID. Do not clear the bug from a precheck-only symbolic fixture.

### C4 — P1: ambiguous ref publication can trigger destructive rollback after state actually committed

`lists::publish` (`lists/mod.rs:271–280`) and `virtuals::publish` (`virtuals.rs:575–580`) recover a failed update-ref acknowledgement by rereading state and accepting an exact new object. But a failed reconciliation read propagates via `?` as an ordinary error, indistinguishable from a proven uncommitted transaction.

In shelf/unshelve (`lists:690–711`), that error drops Index without accept/uncertain, then `working_transaction::apply_with_commit` rolls files back for any commit error (`working_transaction.rs:249–267`). Virtual toggle/undo supply their publication to the same API (`virtuals:856–871,1048–1055`). Thus refs/state may already say shelved/active/undone while index and files are reverted. A further state advance can also make a committed exact object cease to be current before the reconciliation read. Ordinary changelist commit has a separate HEAD uncertainty branch, but shelving and virtual materialization do not.

**Fix:** distinguish committed, proven uncommitted and unknown. A lost acknowledgement plus failed/changed receipt is unknown: retain current materialization/index and backups, record a durable pending operation identifier, block retries and require exact reconciliation. Do not roll back on unknown. Model acknowledgement loss followed by failed receipt read first, without executing Git/cancellation. A generic Result<(),String> callback is insufficient to encode this contract.

### C5 — P1: deferred replay rereads unvalidated .git metadata after its ownership check

`deferred.rs:343–352` calls owned(), which validates root identity, .git, registration and backlink, then rereads .git and parses its gitdir into a metadata argument without applying ownership_paths again. `owned_command` puts it in separate argv; the fixed alias at `:321` verifies only cwd device/inode before invoking Git with that --git-dir. The later filesystem_owned check at `:358` occurs after the command.

**Source interleaving:** after owned succeeds, replace candidate .git with a regular file naming a foreign repository metadata directory. The second read accepts that string; the candidate root remains the expected inode so the alias passes its stat check. Git can mutate foreign HEAD/rebase metadata while using the owned work folder. A subsequent check/error does not undo the foreign metadata write. Even a checked metadata pathname is not a retained identity if its registration directory is later replaced. Separate argv prevents shell injection but does not authenticate the metadata target.

**Fix:** carry validated metadata identity from one observation into dispatch, bind common/worktree metadata using retained ownership suitable for the native process boundary, and refuse any unbound .git/registration change before Git starts. Validate postconditions as well, but not as the only protection. Recording must substitute .git between observations and assert zero mutation dispatch. The existing pure string/cwd-order test never exercises this split. Actual owned-cwd/supervisor fixtures remain unvalidated and held.

### C6 — P2: durable outbox autosend approval is not bound to the selected profile/account

`outbox::Entry` (`outbox.rs:20–35`) stores source/OID, endpoint digests, common-dir string and a routing digest, but no profile identifier or non-secret account/connection identity. The digest (`:66–91`; `push_preflight.rs:119–146`) covers routing/signing/author settings and deliberately excludes credentials. Autosend obtains the currently active profile at execution (`repo/repository_tools/outbox.rs:25–34`) and whichever tab credentials the mutation helper clones (`repository_tools/mod.rs:439–449`). The queue ref is common to worktrees/profiles. Two profiles with identical Git config but different credentials are indistinguishable to the durable approval.

After an offline autosend opt-in under account/profile A, switching to B with the same route and author values can send the queued commit under B without pausing for renewed consent. Additionally the prepare completion at `repo/.../outbox.rs:73–79` checks path/dialog request but not captured profile/account; a stale preparation can be accepted and sent using later credentials. Exact current preflight sets expected_accounts empty (`push_preflight.rs:859–862`), a known lower dependency; even fixing fresh scans does not by itself bind the original queued approval.

**Fix:** pin non-secret profile/connection/principal identity and effective endpoint context at enqueue, revalidate before autosend and reviewed execution, and pause on any change. Require explicit renewed approval for changed account. Invalidate async preparation on profile/connection generation changes. Test with recording profiles whose Git routing/author config is identical but account generations differ; do not call helpers/HTTP during this hold.

### C7 — P2: rebuilding the entire index loses unrelated intent-to-add semantics

`lists::final_index` (`lists/mod.rs:410–462`) rebuilds all entries from mode/OID via tree(), which does read-tree --empty and index-info (`drafts/mod.rs:538–556`). It reconstitutes only skip-worktree and assume-unchanged. Source retains complete original cache bytes but the reconstruction does not preserve other entry flags. In particular CE_INTENT_TO_ADD is not represented in Source.index and is not restored.

**Static repro expectation, not run:** an unrelated path added with intent-to-add has an empty-blob entry and the intent flag. Commit or shelf a different list. The reconstructed index makes that unselected entry an ordinary staged empty file rather than retaining its intent state. UI's promise that other staged contents remain is false even with no external writer. Sparse/split and opaque extension preservation also require explicit audit; this finding specifically identifies the absent intent flag.

**Fix:** start from a full private copy of the captured index/cache and change only selected entries with Git plumbing, preserving unrelated flags/semantics, or explicitly refuse formats that cannot be retained before mutation. Add a recording/index-format contract and, only once allowed, an owned Git regression comparing unrelated intent/staged flags before/after.

### C8 — P1: 32 MiB working snapshot limit is enforced after retaining all file bytes

`lists::read` (`lists/mod.rs:132–148`) bounds paths to 2000, reads each regular file up to 8 MiB, inserts it in the retained map, and only after the entire loop checks TOTAL_LIMIT. Five 8-MiB changed files already allocate 40 MiB before refusal; the allowed 2000-path input can request16,777,216,000 bytes (~15.625 GiB) before a claimed 32-MiB guard. This can exhaust the application worker/process while merely opening lists. virtual::read calls lists::read and then similarly loads missing owned paths before its aggregate sum (`virtuals.rs:434–459`).

This is a source allocation-order proof and arithmetic, not measured large allocations or a stress run. **Fix:** enforce a checked running remaining budget before retaining each buffer, ideally bounding the read by remaining allowance and refusing growth, and apply the same rule to owned-path augmentation. Recording large sizes must prove no subsequent read/allocation request after the budget is exhausted; don't allocate the payload in the test.

### C9 — P2: unshelve can create two active owners for one file

Assign (`lists/mod.rs:342–364`) deliberately removes a path from other active lists but leaves shelved ownership. Unshelve (`:628–641`) only verifies that current bytes/index match shelf base, then clears shelf; it never checks another active list's ownership. UI (`repo/repository_tools/lists.rs:158–195`) promises one active owner and displays only the first matching list.

**Deterministic reachable flow:** shelve A containing f; assign its now-base f to active B (metadata only, permitted because read includes shelved paths); unshelve A before editing f. Its byte/index guards pass, both A/B become active owners, and B's commit action now includes restored A contents. The combo hides the second owner by selecting only the first. No race is required.

**Fix:** refuse unshelve when paths have another active owner or present explicit ownership transfer and update both lists atomically. Add a pure metadata state-transition regression plus the later held owned-file flow. Consider explicit symmetric coordination with virtual ownership as well; current virtual toggle refuses active named-list paths while named-list shelving does not consult virtual ownership. The latter is noted as an adjacent policy question, not a tenth independently asserted blocker.
