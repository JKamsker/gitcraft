## Remaining findings

### R2-B1 — P2: standalone merge lock cleanup can unlink a foreign replacement

**Source-confirmed; predates this correction series.** `src/standalone/save.rs:276-285` implements `Lock::drop` by reading `.gitcraft-merge-<hash>.lock`, comparing the opened identity with the retained lock identity, then calling `Directory::remove_file` on that mutable basename. `src/standalone/directory.rs` implements removal as directory-relative `unlinkat` on Unix and `remove_file` on Windows. A held directory pins the parent, not the name→inode association.

Exact interleaving: Drop opens owned lock A and passes the identity comparison; another actor renames A away and creates foreign lock B at the public basename; Drop unlinks B. A regular replacement loses its bytes/lock, and a symlink replacement loses the foreign directory entry. No output-destination overwrite is necessary. This can occur on successful save or any error return that drops the reservation, and invalidates preservation of unrelated locks. It does not imply the original index-corruption bug still exists: the new index transaction uses capture/inspect/restore instead.

Correction: apply the safe owned-release discipline to standalone reservations, including error paths. Capture the public lock entry into an owned private recovery directory, inspect the inode that actually moved, and retain/restore a foreign entry only into absence. Do not treat a pre-unlink check as conditional unlink. Keep recovery alive through release; surface uncertainty instead of reporting successful complete cleanup. Add a deterministic fixture hook between the identity observation and release that substitutes a regular file and symlink, and prove foreign entries/bytes survive. This review did not run a timing-sensitive live race or edit source to add a hook; the interleaving is established by the exact production sequence.

### R2-B2 — P2: new remote Linux/WSL metadata reader loads all xattr values before enforcing its 1 MiB budget

**Introduced by the correction's new remote transaction helper.** `src/git/file_comparison/remote_index.py:57-59` builds a complete list using `os.getxattr` for every name returned by `os.listxattr`. The 1,024-entry / 1 MiB check runs only afterward in `access` at `:85-90`. Unlike the Darwin branch at `:65-75`, it neither queries sizes nor checks a running budget before loading/retaining values. Snapshot reads invoke `access` twice, so oversized metadata can amplify repeated allocation before eventually refusing. The helper's `RLIMIT_FSIZE` bounds file writes, not resident allocations.

**Independent pure recording reproduction:** parsed the exact immutable helper with Python AST, extracted only its `xattrs`, `access` and `native_acl` function definitions, and executed them against recording fake `os`/`sys` objects; no helper main, process, signal, transport or real xattr operation ran. A synthetic Linux snapshot offered 1,025 names with 65,536-byte values. Production functions requested all **1,025 values / 67,174,400 bytes** before raising `Index access metadata exceeds 1 MiB`. This is an allocation-order proof, not a native Linux filesystem fixture or claim about every filesystem's xattr capacity. Evidence: `/private/tmp/gitcraft-fileviews-core-r2-be013726/remote-xattr-recording.json`, also embedded in the review manifest.

Correction: reject excessive names/count first; use descriptor-based size queries and a checked aggregate budget before allocating each value, then verify actual read length and recheck drift. The existing Darwin approach provides the intended ordering, but use the correct Linux native signatures. Add pure recording gates proving no value read is requested after the total would exceed 1 MiB, count overflow is refused before fetching values, and size/read growth is refused. Preserve full policy or fail closed; do not solve this by silently dropping access metadata. No native Linux/WSL runtime approval is inferred from the synthetic result.
