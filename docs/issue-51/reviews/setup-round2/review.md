## R2-F4 — P2: push-only routing edits leave the old retry challenge current

Source: `repo/https_recovery.rs:5-30`, `repo/load.rs:519-523`, `git/refs.rs:215-250`, native read backend `git/backend.rs:294-320`, and `repo/operations.rs:205-231`.

A Ticket captures `self.remotes: Vec<git::Remote>`; each Remote contains only name and one fetch URL. CLI parsing keeps the first row per remote name; the native backend likewise reads the first `remote.<name>.url`, never `pushurl`. Reload invalidates a challenge only if that incomplete list changes. `https_ticket_current` compares the same list, path, profile context and generation; `sign_in` does not compare `reads` or revalidate the effective operation endpoints. After accepting a matching old scope it calls `run_last_op_again`, which executes the original remote-name command under whatever repository routing configuration exists then.

Source-derived sequence, not executed:

1. A push to origin fails at `https://old-push.fixture.invalid/team/repo`; an old-endpoint challenge is displayed.
2. Change only `remote.origin.pushurl` to `https://new-push.fixture.invalid/team/repo`, leaving fetch `https://fetch.fixture.invalid/team/repo` and the profile unchanged. Even after normal reload, both old/new `Remote` lists are identical, so no challenge invalidation occurs.
3. Sign in to the old challenge. Every Ticket check passes, but retrying `push origin …` now uses the new push route.

This establishes stale workflow authorization, not an independently observed cross-host token leak. A correct lower-level exact credential scope should withhold the old token from a genuinely different destination; that protection is separately under review. It does not make the UI retry current or fulfill the promised route/generation check. Similarly URL rewrite, branch push override and additional pushurl changes can alter routing without changing the retained fetch display field.

Required correction: retain/revalidate an operation-specific effective endpoint/configuration generation at completion and retry, including all push URLs, relevant rewrite/default/override inputs and the captured profile. Changes must invalidate the old challenge even if the fetch display is identical. Acquire/check that metadata off the UI thread or use already loaded immutable route state; do not add Git execution to `https_ticket_current` painting/action paths. Preserve the accurate outcome of a rejection that already ran while discarding its stale UI continuation. Add a pure/recording fixture for pushurl-only edit and unchanged fetch, plus routing override/rewrite changes. The already added `switch_https` read-counter check only guards its asynchronous rejection completion; it does not protect the later sign-in retry path.

## R2-F6 — P2: an incidental earlier URL is treated as the confirmed failed endpoint

Source: `git/command/endpoints.rs:64-82`, `repo/https_recovery.rs:42-65`, `repo/dialogs/remote.rs:90-151`, `repo/operations.rs:175-201`.

`AuthFailure::from_error` splits the entire error on quotes/whitespace, filters syntactically acceptable HTTP URLs and selects `.next()`. Presence of that token sets `confirmed=true`; the parser does not require an authentication failure record or relate it to an attempted route. Thus an earlier remote server/help URL overrides the actual endpoint later in the error and discards the genuine captured candidates.

Concrete source-derived input, not executed:

```text
remote: See https://docs.fixture.invalid/auth for help.
fatal: Authentication failed for 'https://push.fixture.invalid/team/repo'
```

with attempted `["https://push.fixture.invalid/team/repo"]` selects `["https://docs.fixture.invalid/auth"]`, confirmed=true. Both URLs satisfy the candidate URL validator. `offer_failed_https_signin` consequently preselects the docs URL; with one confirmed endpoint the dialog does not ask the user to disambiguate. “Forget stored account and switch…” passes that wrong URL to `https_reject`, while Sign in builds a scoped credential for the same wrong destination. This is the original wrong-endpoint failure in a different input route, introduced by the F6 correction's new free-text URL extractor. No credential was actually erased or sent in this review.

Required correction: recognize structured authentication-failure endpoint evidence, not an arbitrary first URL in mixed/untrusted output. Prefer the actual final Git authentication failure record, validate against captured destinations where appropriate, and handle Git LFS auth endpoint records explicitly without turning unrelated links into confirmed destinations. When evidence conflicts or is ambiguous, require a visible explicit choice; do not silently mark a URL confirmed. Add fixtures with a remote help URL before a real failure URL, several incidental URLs, multi-push candidates and genuine LFS authentication records. Such fixtures must remain pure/recording under the current execution hold.

Additional API contract gap (not a separately proven UI regression): `operation_endpoints` recognizes `--repo=<name>`, but skips the operand of separate `--repo <name>` as if it were an unrelated option (`endpoints.rs:107-128`), allowing the next refspec to be mistaken for the remote. No candidate production UI caller emitting that spelling was established in this scope; correct it while making route metadata reliable, and add a pure argument-parser fixture. Literal explicit URLs also need the same effective-rewrite policy as named routes before they can be described as authoritative fallback candidates.
