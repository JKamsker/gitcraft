## Authentication: root route proof and opaque reviewed receipts must coexist

The merge-tree's automatic combination leaves two different dispatch paths: ordinary operations pass root `run_step` (captures RouteBinding into OpControl); APPROVED history steps directly call `execute_controlled` (bypass run_step). History then replaces the auth error with an opaque one-shot receipt (`push_preflight.rs:1292,1342–1371`). Merely choosing either auth conflict side loses accepted behavior.

Concrete combination:

- Keep root `Ticket::authorizes_endpoint`, failure partitioning, Context/generation/path/remotes checks, `binding.verify`, and EXPECT_HTTPS_ROUTE retry proof unchanged. An opaque receipt cannot authorize an endpoint outside the captured routes.
- At APPROVED dispatch, capture/retain an authoritative root RouteBinding for **the plan's original-remote push arguments**, obtained from `push_args(&plan)` before its runtime alias substitution. Never capture the synthetic `\0push-preflight` marker or transient opaque alias as the Git route. The existing plan check still checks checkout/config/physical source/URLs before every actual destination push. If route proof cannot be captured, retain root's fail-closed behavior.
- On reviewed authentication failure, consume `take_auth_endpoint(error)` once. Convert that proven endpoint plus the captured binding and initiating Context into root's AuthFailure/control path, explicitly requiring `binding.authorizes_endpoint(receipt_endpoint)` before offering a sign-in/rejection/retry. Use a typed/proven URL path, not parsing the opaque log/status as if it contained a canonical Git URL. Preserve the opaque receipt in logged human diagnostics; do not add raw URL/query/userinfo to them.
- Let root `offer_failed_https_signin` create the ticket and continue root verified retry. Missing/expired receipt, missing binding, foreign endpoint or changed profile/routes remains refusal/recheck; **never** history's default-remote fallback. Ordinary failures retain root's captured failure behavior. This bridge is the one new glue needed by these two accepted interfaces, not a replacement credential API.
