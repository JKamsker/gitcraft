# Arch Linux packages

Two independent package directories are provided:

- `gitcraft`: builds the pinned 0.3.5 release source with its default features;
  supports x86_64 and aarch64 and requires Rust 1.95 or newer.
- `gitcraft-bin`: installs the official x86_64 release archive, verified with SHA-256.

They conflict with each other and install the same executable, launchers, icon,
Dolphin service menu, documentation and licenses. Use pacman for updates.

Copy the desired directory somewhere writable, enter it, and run:

```sh
makepkg -si
```

Run as a normal user. Start with an up-to-date Arch system and `base-devel` installed.
For release validation, build in a clean chroot with Arch's `devtools` (`extra-x86_64-build`)
and inspect the resulting package with `namcap`. Validate aarch64 separately; listing
it in the source recipe is not evidence of an executed ARM build.

## Submit to the AUR

Follow the [AUR submission guidelines](https://wiki.archlinux.org/title/AUR_submission_guidelines).
Check whether `gitcraft` and `gitcraft-bin` already exist before submitting. If a name
is taken, coordinate with its maintainer rather than creating a duplicate package.
Create an AUR account and add your SSH public key in your account settings.
Add your own `# Maintainer: Name <email>` line to each recipe you maintain.

Each package needs its own AUR Git repository. For the binary package, from this checkout:

```sh
checkout="$PWD"
git -c init.defaultBranch=master clone ssh://aur@aur.archlinux.org/gitcraft-bin.git /tmp/aur-gitcraft-bin
cd /tmp/aur-gitcraft-bin
cp "$checkout/packaging/arch/gitcraft-bin/PKGBUILD" .
# Add your Maintainer line, then build and inspect the package before uploading.
makepkg -s
namcap PKGBUILD ./*.pkg.tar.zst
makepkg --printsrcinfo > .SRCINFO
git add PKGBUILD .SRCINFO
git commit -m 'Add gitcraft-bin 0.3.5'
git push origin master
```

Repeat with `gitcraft` in place of `gitcraft-bin` for the source package. Upload
recipes and `.SRCINFO`, never built packages, downloaded archives, or Cargo caches.
An empty-repository warning on first clone is expected for a new package.

For updates, bump `pkgver`, reset `pkgrel` to 1, update the source commit or release
checksum, rebuild, regenerate `.SRCINFO`, commit and push. For packaging fixes to
the same release, increment `pkgrel`. Keep the checked-in `.SRCINFO` files here
in sync using `makepkg --printsrcinfo > .SRCINFO` in each directory.

## Other distributions

The existing release workflow already produces `.deb`, `.rpm` and AppImage files.
Direct downloads can be installed with `apt install ./file.deb` or
`dnf install ./file.rpm` (Zypper on openSUSE). Repository publication is a separate step:

- Debian/Ubuntu: publish a signed APT repository with package indexes and signed
  Release metadata. Configure clients with a repository-specific `Signed-By` key.
  See [Debian's repository guidance](https://wiki.debian.org/DebianRepository/UseThirdParty).
- Fedora/openSUSE: sign RPMs and publish repository metadata generated by
  [createrepo_c](https://github.com/rpm-software-management/createrepo_c), plus a
  client `.repo` file. Build and test against each supported distribution's libraries;
  a generic RPM alone does not establish compatibility.
- For official distribution repositories, maintain source packaging (`debian/`
  for Debian, an RPM spec for Fedora/openSUSE) and follow each distribution's review
  process. This differs from hosting your own binary repository.
- [Flathub](https://docs.flathub.org/docs/for-app-authors/submission) is an additional
  cross-distribution desktop route. Gitcraft's host Git, terminals, credentials and
  repository access need deliberate sandbox integration before a Flatpak submission.

No AUR upload, package installation, or repository publication is performed by
adding these recipes.
